# droidjig — Whole-System Audit (2026-08-15)

Scope: the entire repository — Python runtime, Kotlin companion, tests, CI, docs, packaging,
and distribution posture. Commissioned against two goals: **(a) is this defensible as a
portfolio/resume project**, and **(b) what stands between it and actual users**.

Method: full test-suite run, coverage measurement, targeted code review of the safety-critical
paths, hands-on reproduction of failure modes with a synthetic `adb`, and verification of the
project's own stated invariants against the code.

---

## Verdict

**(a) Resume: yes, already — and it is stronger than most things that get put on a resume.**
The engineering discipline here is the selling point, not the feature list. Three artifacts do
the heavy lifting: the `runtime.run_action` choke-point, the 835-test hermetic suite, and the
self-commissioned adversarial review with all 16 findings remediated in-repo. Very few
personal projects have any of those; almost none have all three.

**(b) Popularity: blocked — but not by the code.** The code is ready. Distribution and
positioning are not. At the time of the audit a stranger could not `pip install` it (the name
was taken by someone else — since resolved by the rename to `droidjig`), still cannot download
the companion APK (no release), and is told by every document that they need Termux +
PRoot-Distro on the phone — which is false, and is costing roughly the entire addressable
audience. These are all fixable in days, not months.

The gap between (a) and (b) is unusually wide, and unusually cheap to close.

## What is genuinely strong — defend these in an interview

1. **`runtime.run_action` is a real architectural idea, not a wrapper.** One funnel enforces
   mode gate → kill switch → risk classification → policy → rate limit → idempotency → audit,
   and the daemon reuses it *verbatim* so the safety properties are identical in-process and
   over the wire. Named, documented, and actually unbypassed. This is the thing to whiteboard.

2. **Cross-process correctness was thought through.** Finding 11's fix — recognizing that
   module globals protect a long-lived daemon but *not* one-shot CLI invocations, then adding
   an `flock` sentinel and a disk-backed idempotency store — is a distinction most engineers
   never notice. `runtime.py:21-85`.

3. **The adversarial review is the single most impressive artifact in the repo.** Commissioning
   a review against your own work, ranking 16 findings by severity, fixing all of them, and
   keeping the document (including a residual-risk section) in the public repo demonstrates
   more maturity than the feature set does. Do not bury it.

4. **Invariants are documented and hold.** I checked backend isolation directly: no module
   outside `adb_backend.py` reaches `adb`. `companion_setup.py` takes an injected `adb(*args)`
   seam; `providers/ocr.py` and `providers/termux.py` shell out only to non-adb tools, each
   behind an injectable `runner=`. The invariant text is slightly overstated, though — it says
   "never call `subprocess` … from anywhere else", which providers legitimately do. Reword to
   "never call `adb`; every shell-out goes behind an injected `runner=`" so the rule matches
   the (correct) practice.

5. **Hermetic, fast tests.** 835 passing in 4.1s with zero device dependency, plus a `device`
   marker excluded from CI and Kotlin-side contract-parity tests. The suite is usable as a
   development loop, which is why it stayed healthy.

6. **Honest documentation.** "Unit tests prove logic, not topology" is stated repeatedly and
   the docs refuse to claim unvalidated device behavior. That restraint is rare and is worth
   preserving verbatim.

## Defects

> **Remediation status.** D1, D2, D3, D5 and D6 are fixed (see the commits referencing each ID);
> the descriptions below are kept as the record of what was wrong and why it mattered.
> D4 remains open. D6 was found later, by checking CI on PR #56 rather than in the
> original pass — a reminder that "the suite is green locally" and "the project installs
> for a stranger" are different claims.

### D1 — A corrupt state file kills every command with a raw traceback *(highest severity)* — **FIXED**

All state files are written non-atomically with `Path.write_text()` and most are read with an
unguarded `json.loads()`. Any interruption mid-write — `kill -9`, battery death, full disk,
all routine on a phone — leaves truncated JSON that permanently bricks the tool.

Reproduced:

```console
$ printf '{"mode":"auto"' > $DROIDJIG_HOME/config.json   # truncated write
$ droidjig doctor
Traceback (most recent call last):
  ...
json.decoder.JSONDecodeError: Expecting ',' delimiter: line 2 column 1 (char 15)
```

`config.json` is loaded by *every* command, so this takes out `doctor` — the one command whose
job is diagnosing a broken install. The same pattern affects `ratelimit.json`
(`runtime.py:126-132`, verified raising), `daemon.json`, `macro/limits.json`, `memory` stores,
and the `.jsonl` readers in `audit.py:84`, `daemon/records.py:65`, `macro/records.py:43`,
`macro/autonomy.py:51`.

Notably `runtime._load_idempotency` (`runtime.py:30-35`) *does* guard, with the comment
"corrupt/unreadable store must never block actions". The right instinct was there and simply
never generalized.

**Fix:** one `state.py` with `read_json(path, default)` (guarded) and `write_json(path, obj)`
(tmp file + `os.replace`, atomic on POSIX), then route all of the above through it. ~40 lines
plus tests. This is the highest value-per-line change in the audit.

### D2 — `cli.main` only catches `DroidjigError` — **FIXED**

`cli.py:1909-1916` catches `errors.DroidjigError` and lets everything else escape as a
traceback. That gap is *how* D1 reaches the user, and it means the project's structured-envelope
and `user_action` story is bypassed by exactly the failures users will actually hit. Add a
catch-all that renders an unexpected error through `results.err` with a "please file an issue"
`user_action` and a distinct exit code, keeping the traceback behind `--debug`.

### D3 — Token comparison is not constant-time (Python and Kotlin) — **FIXED**

- `daemon/server.py:419` — `if req.get("token") != self._token:`
- `transport/Dispatcher.kt:73` — `req.optString("token", "") != expectedToken`

`hmac` is not imported anywhere in the Python tree. This sits directly under the project's own
Finding 2 threat model ("loopback is not a UID boundary on Android; any local app with INTERNET
can connect"), and an attacker in that model gets unlimited local attempts with no jitter and
no failed-attempt throttling.

**Honest severity: low.** Tokens are 128-bit (`secrets.token_hex(16)`, `SecureRandom` 16 bytes),
so brute force is infeasible and remote timing recovery of a hex string through `memcmp` is
extremely difficult in practice. It is listed because the fix is one line on each side
(`hmac.compare_digest` / `MessageDigest.isEqual`), and because it is precisely what a reviewer
will grep for *after* your adversarial-review document has raised their expectations. Leaving it
costs more in credibility than it does in risk.

### D6 — CI's Python 3.9 lane cannot install, and has been red on master — **FIXED**

Found while checking CI on PR #56, not in the original pass. Every published `mcp` release now
requires Python >= 3.10, so `pip install -e ".[dev,mcp,yaml]"` fails outright on 3.9:

```
ERROR: Could not find a version that satisfies the requirement mcp<2,>=1.0; extra == "mcp"
ERROR: No matching distribution found for mcp<2,>=1.0
```

The install step dies before pytest runs, so the 3.9 lane reports failure without testing
anything. This is upstream drift, not a regression: master's own run on the base commit
(`c46419f`, 2026-08-07) is red for the same reason. It matters because `requires-python` still
declares `>=3.9`, the README still carries a 3.9+ badge, and a stranger on 3.9 following the
README would have `pip install 'droidjig[mcp]'` fail on them with nothing installed.

**Fix (interim):** an environment marker — `mcp = ["mcp>=1.0,<2; python_version >= '3.10'"]` —
which scoped the breakage to the optional transport instead of the whole install.

**What the marker revealed.** With the install fixed, the 3.9 lane got far enough to run pytest
for the first time — and collapsed with 19 collection errors:

```
TypeError: unsupported operand type(s) for |: 'type' and 'NoneType'
```

`ui_parser.py` and `audit.py` use PEP 604 unions (`dict | None`) in function signatures without
`from __future__ import annotations`, so the annotations are evaluated at import time and fail
on 3.9. Both are core modules that nearly everything imports, which is why 19 test files could
not even be collected.

**So droidjig never ran on Python 3.9 at all.** The support claim in `requires-python`, the
README badge, and the CI matrix were all false, and had been for some time. CI could not catch
it because the dependency-resolution failure killed the job at the *install* step, before
collection — one red signal masking a second, deeper one. That is the real lesson here: a lane
that fails early can hide the failure you actually care about, so a job that has been red for a
while deserves reading, not just re-running.

**Fix (final):** on the maintainer's call, **3.9 is dropped** —
`requires-python = ">=3.10"`, CI matrix `3.10 / 3.11 / 3.13`, marker removed (the floor now
guarantees what it was asserting), README badge 3.10+, explicit `3.10`–`3.13` classifiers for
PyPI. No source changes were needed, because the code had already required 3.10+ in practice;
the metadata simply now says what was true all along. **CI is green on 3.10/3.11/3.13.**

### D4 — `cli.py` is the largest and least-tested module

1,916 lines at **69% coverage** — the worst ratio in the repo, against a suite averaging 83%,
and it is the surface every single user touches. The dispatch/arg-parsing layer is also where
the Finding 15 exit-code inconsistencies lived. Splitting it into a command package
(`cli/observe.py`, `cli/act.py`, `cli/companion.py`, …) and lifting coverage toward 85% is the
best remaining test investment.

### D5 — Minor drift — **FIXED**

README and CLAUDE.md both say "836 tests"; actual is 835 passed + 2 skipped (837 collected).
The counts are now stated once, accurately, with the two conditional skips named.
Trivial, but the number is quoted in four places and will keep drifting — derive it or drop the
precision.

## Adoption blockers, in priority order

### A1 — The name `phonectl` was already taken on PyPI — **RESOLVED: renamed to `droidjig`**

> Historical note: this section is deliberately left in the old name. It is the record of why
> the project is no longer called `phonectl`.

```
name         PhoneCTL
version      0.0.1
summary      PhoneCTL Test
author       wakira
uploaded     2016-08-06
```

`pip install phonectl` fetched a stranger's abandoned 2016 test upload. PyPI normalizes names
case-insensitively, so `PhoneCTL` and `phonectl` were the same slot. That gated every other
distribution step, and it is the kind of problem that is very expensive to discover *after* the
name is on a README, a resume, and a talk.

A PEP 541 transfer was available — single release, nearly a decade abandoned, summary literally
"PhoneCTL Test", dead `azurewebsites.net` homepage — but it takes weeks and buys a name that was
only ever a first guess. **The project was renamed to `droidjig` instead**: free on PyPI, no
competing project, and holding `.com`/`.dev`/`.io`/`.sh`.

Two things the naming search turned up that outlived the naming decision:

- **There is real competition, and it took the obvious names.** [MobileUse](https://github.com/MadeAgents/mobile-use)
  (NeurIPS 2025) and [Minitap's mobile-use](https://github.com/minitap-ai/mobile-use) hold
  `mobile-use`; `android-use` is taken too. Both are LLM agent frameworks that bundle the model
  and the planning. droidjig is the deterministic control plane underneath — that distinction is
  the positioning, and the docs should lead with it.
- **The `*claw` space is spoken for.** `phoneclaw` and `droidclaw` each have multiple active
  OpenClaw-derived projects, several describing the same observe→act-over-ADB loop. Any name in
  that family would have read as a derivative.

The `ctl` suffix was a good instinct and is worth keeping in spirit: it signalled "control plane
with an operational contract," which is what the single-writer daemon, audit log, kill switch and
risk policy actually deliver. `jig` carries the same idea from the machinist's side — the fixture
that makes an operation repeatable and precisely targeted, which is the argument against
guess-and-tap agents.

### A2 — It is presented as Termux-only, and it is not

**This is the highest-leverage finding in the audit.** Every document — README, architecture,
setup wizard, CLAUDE.md — describes the runtime environment as Termux + PRoot-Distro on the
device. The code does not require any of that. `adb_backend` shells out to `adb`; the serial is
just config; `connection.ensure()` returns immediately when `get-state` reports `device`, so
the wireless-rediscovery machinery never even engages on a USB link.

I verified the full loop end-to-end against a synthetic USB-attached device — no Termux, no
PRoot, no wireless pairing:

```console
$ droidjig doctor
droidjig: connected (serial=R5CT90ABCDE, state=device)

$ droidjig observe --json
ok= True  provider= AdbBackend  app= com.android.settings
  i=0 'Wi-Fi'      clickable=True [44, 380, 1036, 520]
  i=1 'Bluetooth'  clickable=True [44, 540, 1036, 680]

$ droidjig tap --text "Wi-Fi" --json
ok= True  provider= AdbBackend  risk= low

$ cat $DROIDJIG_HOME/actions.jsonl
{"ts": ..., "verb": "tap", "request_id": "...", "app": "com.android.settings",
 "hash": "ec251787...", "outcome": "ok", "target": {"selector": {"text": "Wi-Fi"}}}
```

Observe → act → audit, working, from a laptop.

The current framing restricts the audience to "people running Debian in PRoot on their phone."
The actual audience is **anyone with a phone and a USB cable, and anyone running an Android
emulator** — which includes every mobile-QA and agent-eval use case, the two places this tool
is most obviously useful. Termux-on-device is a genuinely cool *advanced* mode and should stay,
but it must not be the front door.

Concretely: lead the README with laptop + USB or emulator; add `droidjig setup --usb` (list
`adb devices`, pick a serial, persist it); keep the wireless wizard as the advanced path.

### A3 — Nothing is installable

No git tags, no GitHub releases. The companion APK exists only as a CI build artifact, which
requires a GitHub login to download and expires in 90 days. Python install is `pip install -e .`
from a clone. Ship `v0.1.0`: tag it, attach a signed release APK, publish the wheel once A1
resolves.

### A4 — The README is a manual, not a landing page

1,572 lines / 71 KB. A visitor's first screenful after the fold is a table of contents, then
instructions for installing `adb`. There is no moment where they *see the thing work*.

Split it: README becomes the pitch, one animated demo of the observe→act loop (asciinema or
GIF), a 60-second quickstart, and links. The existing content moves to `docs/cli-reference.md`,
`docs/safety.md`, `docs/providers.md`, `docs/daemon.md` — it is good material, it is just in
the wrong place. Target under 200 lines.

### A5 — No contribution surface

Missing: `CONTRIBUTING.md`, `CHANGELOG.md`, `SECURITY.md`, issue and PR templates, and topic
tags on the GitHub repo. For a tool that automates a person's phone and ships a security review,
having no documented vulnerability-disclosure path is the conspicuous one.

### A6 — The public repo carries internal process docs

`docs/strategy.md` (47 KB) and `docs/roadmap.md` (14 KB) are planning instruments written for
an internal audience, and "Phase 7.1", "Plan 2.2", "§16 #1 → 1.2" appear throughout the
user-facing docs. To an outsider, phase numbering communicates only "unfinished". Move planning
material to a `planning/` directory or the wiki, and rewrite the public roadmap in terms of
capabilities ("Shizuku support, so ADB is not required") rather than phase numbers.

## The two things that would most raise the ceiling

Beyond fixing the above:

1. **An emulator lane in CI.** The docs are admirably honest that unit tests prove logic and
   not topology — but that caveat is now removable. `reactivecircus/android-emulator-runner`
   boots a real Android image on GitHub Actions, so the actual `adb` path, the real
   `uiautomator` XML, and the companion APK could all be exercised on every push. It converts
   the project's single biggest documented weakness into a green badge, and it is the most
   impressive thing that could be added to this repo for portfolio purposes.

2. **A tool-calling demo.** The MCP server exists but nothing shows an agent using it. A
   90-second recording of a model driving a real phone through droidjig — with the audit log
   and the confirm-mode gate visible — is the artifact that makes people share the repo. It is
   also the artifact that makes the safety architecture legible to someone who will not read
   `runtime.py`.

## Closing note

The common failure mode for a project like this is good code nobody can find. That is exactly
where droidjig is. The engineering is already at the level where the interesting question is
distribution — which is a much better problem to have, and a much cheaper one to fix.
